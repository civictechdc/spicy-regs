# Documented column domains

Exact publisher bytes for the documents that *state what values a column may
carry*, and one dated observation of what our published tables actually carry.
Together they are the input to `scripts/check_source_domain_drift.py`, which
reports where the two disagree.

Every capture is bound to its digest, byte length, publisher URL, and
observation timestamp in `documented-enumeration-capture-manifest-v1.json`.
`spicy_regs.sources.source_domains.read_capture` re-verifies digest and length
on every read, and the documented values are parsed out of the bytes on each
run rather than transcribed — a transcription rots quietly, a parse against a
pinned digest cannot.

What the pin proves: that a capture has not changed since it was pinned, so no
value can be edited into or out of a publisher's document without the check
failing. What it does not prove: that these bytes are what the publisher serves
today. Nothing here refetches `source_url`. Both halves of the comparison are
files in this repository, so the result is a function of the tree — a lock on a
dated finding, not a live drift detector. The lock is the useful part: it fails
the moment someone moves one half without moving the ledger with it.

## What each one states

**regulations.gov API v4, three enums.** The whole 60 KB document holds exactly
three `enum` keys, all in one block under a `#Regulations.gov documentation`
comment: `DocumentType` (5 values, lines 893-898), `DocketType` (2, lines
902-904) and `SubmitterType` (3, lines 908-911). Everything else the API
categorizes by — `subtype`, `category`, `organizationType` — is described in
the same document as agency-configurable, so there is no closed list to check
against. Two quirks are load-bearing and are pinned by tests: `- Nonrulemaking `
carries a trailing space that a YAML plain scalar does not, and `Supporting &
Related Material` carries a literal ampersand that is exactly what the API
returns.

**reginfo.gov Unified Agenda RIN data, twenty sentences.** The XSD contains no
`xs:enumeration` at all — every field is `<xs:restriction base="xs:string"/>`
with no facets — and states its controlled lists only as `xs:documentation`
prose of the form *One of the following options: "…", "…"*. Four of those
sentences are read here: `RULE_STAGE` (line 66), `PRIORITY_CATEGORY` (line 50),
`RIN_STATUS` (line 58) and `MAJOR` (line 74). The publisher's own prose repeats
itself — `PRIORITY_CATEGORY` lists `Not Major` twice — so a literal duplicate is
folded into one value and the raw count is kept beside the distinct one rather
than thrown away.

## What is not covered

`TTBL_ACTION` (line 443) is a decided exclusion. It names 34 timetable actions;
the same snapshot's `timetable_json` carries 1,139 distinct actions over 10,533
entries. The publisher's own data treats that field as free text, so a check
against its list would report a thousand findings and gate nothing. Note also
that its sentence opens *One of the following:* with unquoted values, so the
XSD reader could not parse it in any case — the reason and the parser's reach
happen to coincide, and only the reason is a justification.

`federal_register.document_type` has no pinned document stating its list. The
FR API documentation page is not captured here, and a domain nobody published
is not a documented domain.

`comments.category` (documented by `SubmitterType`) and `comments.document_type`
(by the same `DocumentType` list already checked against `documents`) are an
open gap rather than a decision. `comments` is published as a flat
`comments.parquet` monolith like the other tables, so both are observable; they
are uncovered only because the 2026-08-03 observation did not scan that table.
Closing the gap needs a re-observation that includes it.

## The observation

`observed-domain-snapshot-2026-08-03.json` is derived, not captured: for each
declared column it holds the distinct values with their row support, the null
count, and the row count of the table they came from. It is generated by
`scripts/check_source_domain_drift.py --observe --write-snapshot`, so the code
that writes it is the code that reads it back.

It names its inputs: the three published tables it scanned, at
`https://data.spicy-regs.dev/`, as of producer revision `f1fcb8c9c883`, each
with the SHA-256 and byte length the scan actually read. Those digests are
provenance, not verification — nothing recomputes them later, because the
tables are 70 MB and are not checked in. That is the whole reason a 3.7 KB
summary of 2,270,416 rows exists.

## Refreshing it

Two manual steps, neither of them scheduled. The offline comparison runs in CI
through `tests/test_source_domain_drift.py` on every push, so a *changed* file
here is caught immediately; a *stale* one is not, because staleness is invisible
to a check whose inputs are both checked in.

Re-observe against a fresh download of the published tables:

```
scripts/check_source_domain_drift.py --observe --data-dir <dir of published parquet> \
    --observed-at <ISO-8601> --producer-revision <sha> --write-snapshot
```

Re-pin a capture by refetching it from the `source_url` its manifest entry
names, then recording the digest and byte length of what came back. Either step
will surface a real change as a failed test, which is the point of doing them.
