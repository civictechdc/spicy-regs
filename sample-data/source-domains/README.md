# Documented column domains

Exact publisher bytes for the documents that *state what values a column may
carry*, and one dated observation of what our published tables actually carry.
Together they are the input to `tools/check_source_domain_drift.py`, the gate
that reports where the two disagree.

Every capture is bound to its digest, byte length, publisher URL, and
observation timestamp in `documented-enumeration-capture-manifest-v1.json`.
`spicy_regs.sources.source_domains.read_capture` re-verifies digest and length
on every read, and the documented values are parsed out of the bytes on each
run rather than transcribed — a transcription rots quietly, a parse against a
pinned digest cannot.

The captures arrived from RefSpec, which fetched them; RefSpec pinned the same
digests and byte lengths, and the bytes here are identical to the bytes it
verified.

## What each one states

**regulations.gov API v4, three enums.** The whole 60 KB document holds exactly
three `enum` keys, all in one block under a `#Regulations.gov documentation`
comment: `DocumentType` (5 values, lines 893-898), `DocketType` (2, lines
902-904) and `SubmitterType` (3, lines 908-911). Everything else the API
categorizes by — `subtype`, `category`, `organizationType` — is described in
the same document as agency-configurable, so there is no closed list to check
against. Two quirks are load-bearing and are pinned by tests: `- Nonrulemaking `
carries a trailing space that a YAML plain scalar does not, and `Supporting &
Related Material` carries a literal ampersand that is exactly what the API
returns.

**reginfo.gov Unified Agenda RIN data, twenty sentences.** The XSD contains no
`xs:enumeration` at all — every field is `<xs:restriction base="xs:string"/>`
with no facets — and states its controlled lists only as `xs:documentation`
prose of the form *One of the following options: "…", "…"*. Four of those
sentences are read here: `RULE_STAGE` (line 66), `PRIORITY_CATEGORY` (line 50),
`RIN_STATUS` (line 58) and `MAJOR` (line 74). The publisher's own prose repeats
itself — `PRIORITY_CATEGORY` lists `Not Major` twice — so a literal duplicate is
folded into one value and the raw count is kept beside the distinct one rather
than thrown away.

`TTBL_ACTION` (line 443) is the one documented list deliberately not read. It
names 34 timetable actions; the same snapshot's `timetable_json` carries 1,139
distinct actions over 10,533 entries. The publisher's own data treats that field
as free text, and a gate against its list would report a thousand findings and
gate nothing.

## The observation

`observed-domain-snapshot-2026-08-03.json` is derived, not captured: for each
declared column it holds the distinct values with their row support, the null
count, and the row count of the table they came from. It is generated by
`tools/check_source_domain_drift.py --observe --write-snapshot`, so the code
that writes it is the code that checks it.

It names its inputs: the four published tables at `https://r2.spicy-regs.dev/`
as of producer revision `f1fcb8c9c883`, each with the SHA-256 and byte length
the scan actually read. 3.7 KB summarizes 2,270,416 rows — the three tables are
70 MB and are not checked in, which is the whole reason a summary exists.

Regenerate it against a fresh download with:

```
tools/check_source_domain_drift.py --observe --data-dir <dir of published parquet> \
    --observed-at <ISO-8601> --producer-revision <sha> --write-snapshot
```
